## 3. Bug 修复与技术发现

### 3.1 resultStatus 嵌套列表解析 Bug (v2 修复)

**问题**: cqlib SDK 返回的 `resultStatus` 字段为嵌套列表格式 `[[0],[1],[1],[0],...]`，而非项目代码预期的 JSON 字符串。导致 `parse_measurement_result()` 无法解析测量结果，保真度始终为 0。

**修复**: 在实验脚本中新增 `parse_result()` 函数，支持以下格式:
- JSON 字符串: `'{"0": 0.4393, "1": 0.5607}'`
- 嵌套列表: `[[0],[1],[1],...]` (cqlib 实际格式)
- 直接列表: `[0, 1, 1, ...]`

**验证**: v3 实验 50 次任务全部成功解析，无解析失败。

### 3.2 cqlib 查询超时问题 (v2 修复)

**问题**: 项目封装的 `get_task_status()` 方法使用 `max_wait_time=2`（秒）调用 `query_experiment()`，而真机任务实际需要 10-90 秒才能完成。cqlib SDK 在超时后抛出 `CqlibRequestError`，被误判为查询错误。

**修复**: 绕过 cqlib SDK 的 `query_experiment()` 方法，直接使用 HTTP API 轮询:
- 提交: POST `/qccp-quantum/sdk/experiment/submit`
- 查询: POST `/qccp-quantum/sdk/experiment/result/find`
- 轮询间隔: 5 秒
- 超时: 180 秒 (v3 提升至 180s，v2 为 120s)

**验证**: v3 实验中任务平均延迟 19.9s，最长 69.0s，最短 10.7s，全部在超时内完成。

### 3.3 v3 新增容错机制

| 机制 | 说明 | 效果 |
|------|------|------|
| 多机器自动切换 | 检测到校准错误后自动切换到备用机器 (tianyan176-2 等) | v3 未触发（机器全程稳定） |
| 校准错误自动重试 | 校准错误后等待 60s 重试，最多 2 次 | v3 未触发 |
| 机器健康检查 | 每 5 次提交检查一次机器状态 | v3 全程 running |
| 电路轮换 | H 门和 X 门交替使用 | 获得两种门的保真度数据 |

### 4.3 已知限制

1. **机时无法精确计量**: 天衍云 cqlib SDK 和 REST API 均未提供机时余额查询接口，所有尝试的 endpoint 均返回"系统异常"。精确机时需登录网页端查看。
2. **SJF 策略设计缺陷**: 当前 SJF 策略 action=0 (纯经典)，不会触发真机提交。5 个 seed 共 0 次真机调用。这导致 SJF 与 PPO/FCFS 的对比不公平。
3. **仿真奖励与真机奖励混合**: episode 总 reward 中，仿真步骤的奖励为随机生成，真机步骤的奖励基于保真度。两者权重不同，reward 的绝对值意义有限，应关注相对差异。

## 6. 结论与建议

### 6.1 结论

1. **真机链路完全打通**: API 认证 → 任务提交 → 结果查询 → 测量解析 → 保真度计算，50 次任务 100% 成功。
2. **PPO 策略显著优于 FCFS**: PPO 平均 reward 823.45 vs FCFS 385.17，提升 +113.8%，且 5 个 seed 间方差小 (±6.00)。
3. **真机保真度优秀**: 50 次任务平均保真度 0.9446，X 门保真度达 0.9875，H 门保真度 0.9159。
4. **容错机制有效**: v3 的多机器切换和自动重试机制虽未触发（机器全程稳定），但为后续实验提供了保障。

### 6.2 建议

1. **修复 SJF 策略映射**: 将 SJF 的 action 从 0 (classical) 改为 2 (hybrid)，使其也能提交真机任务，保证三策略对比公平性。
2. **增加读出校准**: 使用 cqlib 的 `readout_calibration=True` 参数进行读出误差校正，可提升保真度测量精度。
3. **扩展电路种类**: 当前仅使用 H 门和 X 门，建议增加 CNOT、Toffoli 等多比特门电路的测试。
4. **机时管理**: 建议联系天衍云技术支持确认机时查询 API，或通过网页端定期监控余额。
